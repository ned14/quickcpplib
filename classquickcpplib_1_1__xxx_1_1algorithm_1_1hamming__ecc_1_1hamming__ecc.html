Detailed Description

template<size_t blocksize>
class quickcpplib::_xxx::algorithm::hamming_ecc::hamming_ecc< blocksize >

Calculates the single error correcting Hamming Error Correcting Code for a blocksize block of bytes. For example, a hamming_ecc<8> would be the very common 72,64 Hamming code used in ECC RAM, or a hamming_ecc<4096> would be for a 32784,32768 Hamming code.

This is a Hamming code, NOT a SECDED code

The number of parity bits is chosen by the plain Hamming condition (data bits + parity bits + 1) <= 2^parity bits. That is all this class appends: there is no additional overall-parity bit, and therefore no double error detection. To be unambiguous about what you are getting:

  • It corrects a single flipped bit within one block.
  • It does NOT detect a double bit error. A one bit and a two bit error both produce a syndrome which is the XOR of the positions in error, so for a two bit error at positions a and b the syndrome names some third position c. verify() flips c, which turns the block into a different but perfectly valid codeword, so its own re-check passes and it reports healed on data which no longer matches the original. Wrong data is returned with a success status, silently.
  • A three bit error can also land on a valid codeword (three positions XOR into one), and larger counts are no better behaved. So it is NOT true that only "more than two bits" of error is undefined: there is no error count above one which this code reports as corruption reliably.

Therefore you MUST combine this with a strong hash or checksum over the data (as this documentation has always recommended), and you must not use its return value to conclude that a block is intact. The only sound use is to repair a single flipped bit cheaply once a hash has already told you that something is wrong; it must never be the thing which tells you that a block is fine.

A true SECDED code would need one extra overall-parity bit, which raises result_bits_valid() and changes the wire format of every stored ECC. That is deliberately not implemented: this class has no production users, so an honest name and this documentation are worth more than a new code format.

Warning
This class needs to be completely reimplemented using SSE and AVX. Its current implementation works fine, but performance is far below what it can be.

Did you know that some non-ECC RAM systems can see 1e-12 flips/bit/hour, which is 3.3 bits flipped in a 16Gb RAM system per 24 hours). See Schroeder, Pinheiro and Weber (2009) 'DRAM Errors in the Wild: A Large-Scale Field Study'.

After construction during which lookup tables are built, no state is modified and therefore this class is safe for static storage (indeed if C++ 14 is available, the constructor is constexpr). The maximum number of bits in a code is a good four billion, I did try limiting it to 65536 for performance but it wasn't worth it, and one might want > 8Kb blocks maybe. As with any single error correcting Hamming code, an ECC which is itself incorrect, or a block with more than one bad bit, is not reliably reported as such - see the section above, which is why you must combine this with a robust hash which can tell you definitively if a buffer is error free or not rather than relying on this to do so.

The main intended use case for this routine is calculating the ECC on data being written to disc, and hence that is where performance has been maximised. It is not expected that this routine will be frequently called on data being read from disc i.e. only when its hash doesn't match its contents which should be very rare, and then a single bit heal using this routine is attempted before trying again with the hash. Care was taken that really enormous codes are fast, in fact tuning was mostly done for the 32784,32768 code which can heal one bad bit per 4Kb page as the main thing we have in mind is achieving reliable filing system code on computers without ECC RAM and in which sustained large quantities of random disc i/o produce a worrying number of flipped bits in a 24 hour period (anywhere between 0 and 3 on my hardware here, average is about 0.8).

Performance notes of this current implementation:

For a Skylake CPU:

  • MSVC Fixed buffer: 125.719 Mb/sec, or 23.48 cycles/byte
  • MSVC Variable buffer: 144.167 Mb/sec, or 20.48 cycles/byte
  • MSVC heal: 80.4498 Mb/sec
  • GCC7 Fixed buffer: 201.509 Mb/sec, or 14.65 cycles/byte
  • GCC7 Variable buffer: 317.97 Mb/sec, or 9.28 cycles/byte
  • GCC7 heal: 126.099 Mb/sec
  • cla6 Fixed buffer: 276.962 Mb/sec, or 10.66 cycles/byte
  • cla6 Variable buffer: 210.248 Mb/sec, or 14.04 cycles/byte
  • cla6 heal: 171.174 Mb/sec

Note that better than 1Gb/sec is easily possible if I rewrite the implementation.
